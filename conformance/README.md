# Conformance

The contract between Moat Core (`libs/core`) and every gate (DT-02, FR-05, SEC-63). Plain JSON,
readable without any test framework. Every implementation runs every file; a case is never
deleted or edited to make an implementation pass.

## `vectors/crypto/` (docs/CRYPTO.md §11)

Generated by `pnpm vectors` from `libs/core/scripts/build-vectors.ts`; the core's conformance spec
fails when a committed file differs from the generator. All keys are derived from public labels
and are **TEST ONLY**.

| File             | What                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------- |
| `base64url.json` | strict base64url decoding: `input` → `{ok: true, hex}` or `encoding_invalid`           |
| `json.json`      | strict JSON acceptance: `input` (or `inputHex`) → `{ok: true}` or `json_invalid`       |
| `jcs.json`       | canonical JSON for signers; gates never canonicalise and may skip it                   |
| `kid.json`       | key id and fingerprint per algorithm and public key                                    |
| `bundle.json`    | envelope (+ optional `padTo` with spaces) and gate state → gate id and version, or the |
|                  | rejection code of the first failing check (docs/CRYPTO.md §4.3)                        |
| `secret.json`    | sealed object, the gate's own id and the secret's name → plaintext hex or rejection    |

Every case has a `name` and an `expect`: `{ "ok": true, … }` or `{ "ok": false, "error": "<code>" }`.
The codes are the closed list in `libs/core/src/errors.ts` and `gates/php/src/RejectionCode.php`.

| `keyfile.json` | key file + passphrase → `{ok: true, kid}` or `keyfile_invalid` / `keyfile_locked` (core, Desktop and CLI only; a gate never opens a key file) |

## `vectors/http/` and `vectors/config/`

Generated by the same `pnpm vectors` (`libs/core/scripts/build-format-vectors.ts`).

| File                     | What                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------ |
| `http/path.json`         | raw request path → normalised path or `path_invalid` (SEC-42)                                          |
| `http/content-type.json` | `Content-Type` header + allowed media types → `{ok}` (FR-18)                                           |
| `http/cors.json`         | route origins + `Origin` → allowed origin or `origin_forbidden`; preflight answers (FR-15)             |
| `http/rate-limit.json`   | request times against limits → allowed / `retryAfter`; `REMOTE_ADDR` → client key (FR-30, SEC-26)      |
| `config/config.json`     | compiled config + the bundle's secret names → `{ok: true}` or `config_invalid` (step 9)                |
| `config/policy.json`     | compiled config + local policy → `{ok: true}`, `policy_violation` or `policy_invalid` (SEC-10, SEC-11) |

## `http/`

Request-level cases against a **running gate**, written by hand. `http/gate.json` holds one
config, one local policy, the secrets to seal and the cases; the runner builds the gate file,
installs it through its own CLI, serves it with a web server (`php -S` for PHP) and points it at a
fake HTTPS upstream on 127.0.0.1 through the policy's `testing` block. Every case names the
answer the client gets and how many requests reached the upstream; the planted secret must never
appear in an answer or the gate's log. PHP: `gates/php/tests/Http/`.

for CORS, rate limits and the lazy pull once the gate has them.
